1. Resumen Ejecutivo
Este documento describe la arquitectura, esquema de base de datos, lógica de cálculo y wireframes funcionales del Módulo de Proyección de Caja (Tab 2) que se agregará a la aplicación FLUJO_CAJA existente.

1.1 Cambios respecto a v2.0

#	Cambio	Justificación	Impacto
1	Eliminación de la capa Make + Google Sheets como bus de datos principal	Reducción de puntos de fallo. La carga directa via Excel export es más robusta y universal	CRÍTICO
2	Nuevo patrón de carga universal: upload Excel CxC/CxP (igual que Tab 1 con cartolas)	Funciona con cualquier ERP que exporte Excel, no solo Kame. Sin API, sin costo adicional	CRÍTICO
3	Tabla proyeccion_remuneraciones para persistir datos de remuneraciones	Elimina fragilidad del parser volatil. Los datos persisten entre proyecciones	IMPORTANTE
4	Modo operación dual: carga manual + integración futura opcional	El sistema funciona desde día 1 sin APIs. La integración Make/API es capa adicional no bloqueante	IMPORTANTE
5	Desacoplamiento explicito Tab 1 / categorias_financieras	Tab 1 nunca lee la tabla maestra. Coherencia por convención de nombres, no por FK	IMPORTANTE
6	Snapshots versionados mantenidos de v2.0	Sin cambios — es la decision mas importante del diseño anterior	CRITICO

PRINCIPIO FUNDAMENTAL	Tab 1 no se toca bajo ninguna circunstancia. Todo el código nuevo va en archivos separados. Tab 1 es producción con cliente real.

 
2. Arquitectura General

Componente	Tecnología	Rol
Frontend / Backend	Streamlit + Python	Interfaz, lógica de negocio, parser de archivos
Base de datos	PostgreSQL (existente)	Persistencia de todos los módulos + snapshots
Carga de datos ERP	Upload Excel (CxC / CxP)	Cliente exporta desde su ERP y sube el archivo — igual que Tab 1 con cartolas
Carga de remuneraciones	Upload Excel (libro de sueldos)	Parser normaliza y persiste en tabla propia
Integración futura (opcional)	Make + API ERP	Capa adicional que alimenta las mismas tablas. No bloquea arranque
IDE	Cursor	Desarrollo asistido por IA
Deploy	Render (existente)	Producción — solo desde branch main

2.1 Flujo de Datos
El flujo de datos sigue el mismo patrón que Tab 1, extendido para tres fuentes adicionales:

Fuente	→	Acción	→	Destino
ERP (cualquier: Kame, Defontana, Bsale…)	→	Cliente exporta Excel CxC / CxP y lo sube a la app	→	PostgreSQL (proyeccion_facturas + proyeccion_cargas)
Libro de sueldos Excel	→	Cliente sube archivo, parser normaliza	→	PostgreSQL (proyeccion_remuneraciones)
Formulario importaciones	→	Ingreso manual en la app	→	PostgreSQL (proyeccion_importaciones)
Parámetros fiscales usuario	→	Configuración inicial + ajustes	→	PostgreSQL (proyeccion_parametros_usuario)
Make + API ERP (futuro, opcional)	→	Carga automática periódica	→	Mismas tablas PostgreSQL — mismo destino

CLAVE v3.0	PostgreSQL es la única fuente de verdad. Los archivos Excel son medios de entrada temporales, no fuentes persistentes. Esto elimina la dependencia de Google Sheets como bus de datos.

 
3. Patrón Universal de Carga (Nuevo en v3.0)
Este es el cambio arquitectural más importante respecto a v2.0. Reemplaza la dependencia de API Kame + Make + Google Sheets por un mecanismo de carga directa universal.

3.1 Concepto: Upload Excel igual que Tab 1
Tab 1 ya demuestra el patrón correcto: el cliente sube un Excel (cartola bancaria), el sistema lo parsea, lo guarda en BD, y puede consultarlo n veces sin re-subir. Tab 2 adopta exactamente el mismo patrón para CxC y CxP.

Tab 1 (existente)	Tab 2 (nuevo)
Cliente sube Excel de cartola bancaria	Cliente sube Excel de CxC exportado desde ERP
Parser lee columnas del banco	Parser lee columnas estándar: fecha_vencimiento, saldo, razón_social
Datos guardados en BD con fecha de carga	Datos guardados en proyeccion_facturas con fecha_carga
Cliente puede consultar análisis sin re-subir	Cliente puede generar proyecciones sin re-subir
Nueva carga reemplaza la anterior	Nueva carga crea registro en proyeccion_cargas (historial)

3.2 Compatibilidad con ERPs
El parser acepta cualquier Excel de CxC/CxP que contenga las columnas mínimas requeridas. Las columnas adicionales se ignoran sin error.

Campo requerido	Kame	Defontana	Bsale / Otros
fecha_vencimiento	Fecha Vencimiento	Fecha Vto	Fecha Vencimiento
saldo	Saldo	Monto Pendiente	Saldo
razon_social	Razón Social	Cliente / Proveedor	Razón Social
monto_total	Total Doc	Monto Total	Total
fecha_emision (opcional)	Fecha Emisión	Fecha Emisión	Fecha

ESCALABILIDAD	El parser puede extenderse con un archivo de mapeo de columnas por ERP (YAML/JSON). Esto permite agregar nuevos ERPs sin tocar código Python — solo se agrega el mapeo.

 
4. Proyecciones Versionadas (Crítico — mantenido de v2.0)
PUNTO MÁS IMPORTANTE DEL DISEÑO	Sin snapshot histórico, cada recálculo sobreescribe la proyección anterior. No es posible responder: ¿qué proyectábamos para abril hace 3 semanas y qué pasó realmente?

Cada proyección generada se guarda como snapshot versionado en BD. El usuario puede comparar snapshots anteriores contra el flujo histórico real (Tab 1), midiendo calidad del modelo.

Esto permite:
•	Comparar proyectado vs real por categoría y periodo
•	Detectar dónde el modelo consistentemente se equivoca
•	Dar trazabilidad al cliente — puede ver la evolución de sus proyecciones
•	Medir la calidad del servicio de Kappo en el tiempo

 
5. Módulos del Sistema
Módulo 1 — Facturas ERP (CxC / CxP)
NUEVO en v3.0: carga por upload Excel, sin dependencia de API ni Make.

Aspecto	Descripción
Fuente de datos	Export Excel desde cualquier ERP — mismo archivo que el cliente ya usa
Mecanismo de carga	Drag & drop en la app (igual que cartola en Tab 1)
Parser	Lee columnas mínimas + ignora extras. Mapeo configurable por ERP
Persistencia	proyeccion_facturas en BD. El Excel es descartable después de la carga
Historial de cargas	proyeccion_cargas registra cada upload con fecha, usuario y origen
tipo_confianza	real si fecha_vencimiento viene directa del ERP, estimado si es calculada
Integración Make/API	Capa futura opcional. Usa las mismas tablas BD sin cambiar nada

Módulo 2 — Importaciones
Sin cambios respecto a v2.0. Ingreso manual via formulario en la app.

Evento	Fecha de impacto en caja	Categoría	tipo_confianza
Pago a proveedor extranjero	fecha_pago_proveedor	PROVEEDORES_EXTRANJEROS	manual
Gastos aduana / flete / seguro	eta_real o eta_estimada	GASTOS_IMPORTACION	estimado
IVA diferido importación	Día 12 mes siguiente a ETA	IVA_IMPORTACION	estimado

Módulo 3 — Remuneraciones (Mejorado en v3.0)
CAMBIO v3.0: los datos de remuneraciones ahora persisten en BD. El Excel ya no es fuente volátil.

Aspecto	Descripción
Carga	Upload Excel libro de sueldos (igual que CxC/CxP)
Persistencia	proyeccion_remuneraciones con campos: empleado, monto_liquido, mes_aplicacion, dia_pago
Estimación	Si no hay carga del mes actual, el sistema usa datos del mes anterior con tipo_confianza = estimado
Imponible	Se calcula proporción imponible para proyección de imposiciones (AFP/Salud)

Módulo 4 — Egresos Paramétricos
Sin cambios respecto a v2.0. Lógica de desfase fiscal:

Parámetro	Tipo	Default	Validación	Obligatorio
tasa_ppm	%	Sin default	WARNING	Sí — bloquea proyección
tasa_retencion_honorarios	%	10.75%	0–30%	Solo si paga honorarios
dia_pago_impuestos	entero	12	1–28	No
dia_pago_remuneraciones	entero	últ. hábil	1–28	No
dia_pago_imposiciones	entero	10	1–28	No

-- Tabla: proyeccion_cargas
CREATE TABLE proyeccion_cargas (

7. Tipo de Confianza por Línea

tipo_confianza	Significado	Origen típico	Color UI
real	Dato confirmado del ERP o cartola	Kame API con fecha_vencimiento directa / upload Excel	Verde
estimado	Calculado por el sistema con reglas	IVA/PPM calculados, ETA sin confirmar	Amarillo
manual	Ingresado manualmente por el usuario	Importaciones, egresos paramétricos	Azul

REGLA DE ADVERTENCIA	Si más del 40% del flujo proyectado es estimado o manual, mostrar warning general indicando baja confianza de la proyección. El número exacto es configurable por parámetro.
